# Docker, database and environment

- Four compose files, each its own project, never mixed:
  - `docker-compose-db.yml` (project `korfbal-db`): only the PostgreSQL for `npm run dev` and the tests (5432, volume `korfbal-stream-kit_pgdata`). `npm run db:up`/`db:down` use it.
  - `docker-compose.yml` (project `korfbal-dev`): the whole app built from the local code, own database: app on 80, API 3333, PostgreSQL 5434, pgAdmin 5050. Always `docker compose up -d --build`: the migrate job runs the migrations baked into the image (`korfbal-stream-api:dev`, shared by migrate and API). Shares ports 80/5050 with localtest: never run both. `npm run docker:restore-backup [-- dump.sql]` (`scripts/restore-backup.sh`) replaces its database with a pg_dump backup (default last season's `../2025-2026-backup/streamz-2025.sql`, OWNER lines dropped) and starts it with `SKIP_SEED=true`; `npm run db:restore-backup` does the same for the `npm run dev` database.
  - `docker-compose-localtest.yml` (project `korfbal-localtest`): see below. Its network has the fixed name `korfbal-network`, which `docker-compose-monitoring.yml` (project `korfbal-monitoring`: Prometheus 9090, Grafana 3000, cAdvisor 8081, Postgres exporter) joins as external: start localtest first, stop monitoring first.
  - `docker-compose-prod.yml`: Docker Hub images at a fixed release tag, `STREAMZ_API_VERSION` / `STREAMZ_KIT_VERSION` with the current versions as default. A release only builds the changed apps, so API and kit tags differ; check a tag with `docker manifest inspect`.
- After `docker compose down -v` (volume wipe) the migrate job seeds again.
- Local dev: `npm run db:up` then `npm run prisma:migrate` before starting the API.
- Never edit the database directly — use migrations (`npm run prisma:migrate`).
- `ASSETS_DIR` defaults to `storage/` in dev and `tmp/test-storage` in tests. Logo directories follow the organization's **slug**; the database stores **only the file name** (ids differ per system, so a backup restored elsewhere keeps working): sponsor logos are `<ASSETS_DIR>/sponsors/<slug>/<file>` (`Sponsor.logoUrl = "<file>"`), organization logos `<ASSETS_DIR>/organizations/<slug>.<ext>` (`Organization.logoUrl = "<slug>.<ext>"`, only the extension counts). Every path or URL of a logo comes from `services/sponsorLogos.ts` (`sponsorLogoRelPath`, `organizationLogoRelPath`, `withLogoSrc`); the API sends `logoSrc` (`/uploads/sponsors/<slug>/<file>`) next to `logoUrl` and the kit only uses `logoSrc`. The vMix carousel/slides keep giving the plain file name. A slug rename (`PUT /api/organizations/:id`) moves `sponsors/<old>` and `organizations/<old>.*` (`renameOrganizationLogoFiles`, `services/logoStorage.ts`): files first, then the database, files moved back when it fails; 409 when anything for the new slug is already on disk, so a reused slug starts empty. At startup (and after a sponsors restore) `migrateLogoStorage` moves the older layouts in (`sponsors/<id>/`, legacy flat `sponsors/<file>` that the organization's sponsors use — copied when another organization uses it too —, `organizations/<id>.<ext>`), idempotent, never overwriting. A sponsor `logoUrl` is never derived from the name (null until an upload); a client value is only accepted when it is the current one or a file in the own directory (`resolveClientLogoUrl`; a backup restore accepts any valid file name). Logo uploads accept only png/jpg/gif/webp, checked on the content, at most 4096×4096 pixels and (PNG) with sound data (`services/imageUpload.ts`, `services/imageSafety.ts`); there is no generic upload endpoint. Files are read for the PDF and the image download only through `readAssetFile`/`assetFilePath` (`services/reportSponsors.ts`): regular files inside the root, no symlinks, size-limited, read once; `doc.image` gets the checked buffer from `pdfImage`.
- **Backup coverage**: the per-entity backups (`routes/backup.ts`) carry every tenant field of persons/skills, positions, matches (also `isManual`), productions (`liveTime`, `setupTime`, `crewCallTime`, callsheet `timeStart/timeEnd`, events `planned*`, `callSheetItemId`, `parentId`, `metadata`, report `matchSponsor/ballSponsor`), sponsors (also `enabled`, `categories`, logo file name) and all `OrganizationSetting` keys. Productions carry `chapters` (name, orderIndex, bezetting) and `chapterOrderIndex` on items and events; files with the old `segments`/`productionSegmentVolgorde` and old segment-template backups are still read. Settings also carry the own club (`ownClubSlug`), the organization details (`organizationDetails`: name, logo, club; a restore never changes the target's slug or `isActive`) and the seasons' `indoorStartDate` by season name (set only when the season exists without one). Images: `GET /api/backup/images` (zip relative to `ASSETS_DIR`). Not carried, intentionally: `MatchSource` and API keys (secrets); also not carried: callsheet/title templates, `PositionLink`, `MatchRoleAssignment` (the standard set covers most).
- **Base images are Docker Hardened Images** (`dhi.io/node`, `dhi.io/nginx`); run `docker login dhi.io` (Docker Hub account) once before building. `-dev` variants only in build stages; runtime images have no shell, no npm/pnpm and run as non-root (API as uid 1000, nginx on port 8080 → host 80). Hence: the migrate job runs `node /app/seed/migrate-and-seed.cjs`, healthchecks use `node -e fetch(...)`, Prisma engines are pinned via `PRISMA_QUERY_ENGINE_LIBRARY`/`PRISMA_SCHEMA_ENGINE_BINARY`. PostgreSQL still uses the official `postgres:16-alpine` image.
- **Local image test against a backup**: `docker-compose-localtest.yml` (project `korfbal-localtest`, ports 80/3334/5433) builds the images and fills its own db from a pg_dump SQL file on first start (`LOCALTEST_SQL`, default `../2025-2026-backup/streamz-2025.sql`); the migrate job runs with `SKIP_SEED=true`. Images come from a bind mount on the local disk (`LOCALTEST_STORAGE`, default `./storage`), so they survive restarts. Reset the db to the backup: `down -v` then `up -d`. The API serves `/uploads` and `/storage` from `ASSETS_DIR`; there is no separate uploads dir.
- **Docker Hub overview**: `apps/<app>/DOCKERHUB.md` is published as the repository description on Docker Hub by the `merge` job in `ci.yml`, on releases only. Keep it up to date when env vars, ports or the purpose change.
- **No secrets in checked-in config**: compose files read them via `env_file` from local, gitignored files — `secrets.env` (dev, optional), `secrets.prod.env` (prod), `streamz-test/secrets.env`. Templates: `secrets.env.example`, `secrets.prod.env.example`. Don't use a root `.env`/`.env.local` for this: Nx loads those into every task.

## Environment Variables (API)

Validated with Zod at startup (`apps/korfbal-stream-api/src/config.ts`):

```
DATABASE_URL=postgresql://korfbal:korfbal@localhost:5432/korfbal
PORT=3333
SCOREBOARD_BASE_URL=http://<scoreboard-ip>/scoreboard
SHOTCLOCK_BASE_URL=http://<shotclock-ip>/shotclock
ASSETS_DIR=storage
HOST_IP=<optional, for vMix endpoint auto-detection in Docker>
DEBUG_LOGGING=<optional, true: also log every successful GET (vMix, scoreboard polling) and the vMix data source content; LOG_LEVEL overrides>
```

The match import is not an env var: each organization configures its source (provider, URL, token) in Beheer → Setup → Organisatie → Wedstrijdimport (`MatchSource`).

In tests, `.env.test` is loaded automatically.
