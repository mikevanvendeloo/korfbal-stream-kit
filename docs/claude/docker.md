# Docker, database and environment

- **`distribution/`** holds every compose file, the deployment scripts, the env templates (`*.env.example`), the pgAdmin `servers*.json`, the monitoring config, the bridge variants and `local-html`; `distribution/README.md` is the install guide. The folder is copied as a whole to a production machine. Relative paths in a compose file resolve from `distribution/` (the first `-f` file's folder): production data sits next to `docker-compose.yml` (`dbdata/`, `storage/`, `uploads/`, `backups/`, `data/venue-bridge/`, all gitignored); the dev, localtest and dev-bridge files point back into the repo (`build.context: ..`, `../storage`, `../uploads`, `../data/venue-bridge`, `LOCALTEST_SQL` default `../../2025-2026-backup/streamz-2025.sql`). `.dockerignore` excludes `/distribution`. Each file is its own project, never mixed:
  - `docker-compose-db.yml` (project `korfbal-db`): only the PostgreSQL for `npm run dev` and the tests (5432, volume `korfbal-stream-kit_pgdata`). `npm run db:up`/`db:down` use it.
  - `docker-compose-dev.yml` (project `korfbal-dev`): the whole app built from the local code, own database: app on 80, API 3333, PostgreSQL 5434, pgAdmin 5050. Always `docker compose -f distribution/docker-compose-dev.yml up -d --build`: the migrate job runs the migrations baked into the image (`korfbal-stream-api:dev`, shared by migrate and API). Shares ports 80/5050 with localtest: never run both. `npm run docker:restore-backup [-- dump.sql]` (`scripts/restore-backup.sh`) replaces its database with a pg_dump backup (default last season's `../2025-2026-backup/streamz-2025.sql`, OWNER lines dropped) and starts it with `SKIP_SEED=true`; `npm run db:restore-backup` does the same for the `npm run dev` database.
  - `docker-compose-localtest.yml` (project `korfbal-localtest`): see below. Its network has the fixed name `korfbal-network`, which `docker-compose-monitoring.yml` (project `korfbal-monitoring`: Prometheus 9090, Grafana 3000, cAdvisor 8081, Postgres exporter) joins as external: start localtest first, stop monitoring first.
  - `docker-compose.yml` (production, project `streamz`): Docker Hub images at a fixed release tag, `STREAMZ_API_VERSION` / `STREAMZ_KIT_VERSION` with the current versions as default; secrets from `secrets.prod.env` next to it. A release only builds the changed apps, so API and kit tags differ; check a tag with `docker manifest inspect`.
  - `docker-compose.venue-bridge.yml` (production bridge, project `venue-bridge`, own network) and `docker-compose.venue-bridge-dev.yml` (dev bridge, added to the dev or localtest project); see the venue-bridge bullet.
  - **Windows scripts** (`distribution/start.cmd`, `upgrade.cmd`, `start-localtest.cmd`; the PowerShell in `distribution/scripts/`, shared code in `common.ps1`): `start.cmd` starts Streamz and/or the venue-bridge, `upgrade.cmd [-Version x | -Api x -Kit y -Bridge z] [-Only streamz|bridge]` pulls the given or latest release tag per app (Docker Hub API) plus the latest `postgres:16-alpine` patch, dumps the database to `backups/` first when the API version changes, and writes the versions to `streamz.local.env` (gitignored, template `streamz.local.env.example`; also holds `RUN_STREAMZ`/`RUN_BRIDGE`, `BRIDGE_VARIANT` and the bridge's `API_URL`/`API_KEY`). Both pass that file as `--env-file`. Before starting they refuse when `dbdata` still sits in the folder above (the layout before the move, when the folder is used inside the old checkout) or when the API or bridge service runs in another compose project (the old project named after the repo folder or `compose`, localtest, dev): ports would clash; without a `dbdata` next to the compose file they ask before starting on an empty database (`-Yes` skips). On a production machine the contents are copied into an own folder (e.g. `C:\streamz`); its name does not matter, the compose files fix the project names. Keep the `.ps1` files ASCII (PowerShell 5.1 reads BOM-less files as ANSI).
- After `docker compose down -v` (volume wipe) the migrate job seeds again: only the current season and the standard roles; the organizations themselves come from a migration and get the full standard set at API startup (no positions yet). Persons, sponsors and draaiboeken come from an import.
- Local dev: `npm run db:up` then `npm run prisma:migrate` before starting the API.
- **Prisma 7**: `prisma.config.ts` (repo root) holds the schema, migrations and seed paths and the connection (`DATABASE_URL` from the environment; Prisma no longer loads `.env`, the npm scripts use dotenv-cli, the tests `.env.test`, the image its environment). `prisma generate` writes the client (CJS) and the tenant-scope model metadata (`prisma/model-metadata-generator.cjs`, a second generator, because Prisma 7 has no `Prisma.dmmf`) to `apps/korfbal-stream-api/src/generated/` (gitignored): run `npm run prisma:generate` after `pnpm install`; CI, the Dockerfile and `api:dev` do. Import it as `@korfbal-stream-kit/prisma` (tsconfig/Vitest alias; the kit may only `import type` from `@korfbal-stream-kit/prisma-enums`). Every client gets a driver adapter from `createPrismaAdapter()` (`services/prismaAdapter.ts`, pg pool with the 5 s connect timeout Prisma 6 had); never `new PrismaClient()` without it. The image bundles the client into `main.js` and the seed into `seed/prisma/seed.js`; the migrate job runs `prisma migrate deploy --config=/app/prisma.config.ts`.
- Never edit the database directly — use migrations (`npm run prisma:migrate`).
- `ASSETS_DIR` defaults to `storage/` in dev and `tmp/test-storage` in tests. Logo directories follow the organization's **slug**; the database stores **only the file name** (ids differ per system, so a backup restored elsewhere keeps working): sponsor logos are `<ASSETS_DIR>/sponsors/<slug>/<file>` (`Sponsor.logoUrl = "<file>"`), organization logos `<ASSETS_DIR>/organizations/<slug>.<ext>` (`Organization.logoUrl = "<slug>.<ext>"`, only the extension counts). Every path or URL of a logo comes from `services/sponsorLogos.ts` (`sponsorLogoRelPath`, `organizationLogoRelPath`, `withLogoSrc`); the API sends `logoSrc` (`/uploads/sponsors/<slug>/<file>`) next to `logoUrl` and the kit only uses `logoSrc`. The vMix carousel/slides keep giving the plain file name. A slug rename (`PUT /api/organizations/:id`) moves `sponsors/<old>` and `organizations/<old>.*` (`renameOrganizationLogoFiles`, `services/logoStorage.ts`): files first, then the database, files moved back when it fails; 409 when anything for the new slug is already on disk, so a reused slug starts empty. At startup (and after a sponsors restore) `migrateLogoStorage` moves the older layouts in (`sponsors/<id>/`, legacy flat `sponsors/<file>` that the organization's sponsors use — copied when another organization uses it too —, `organizations/<id>.<ext>`), idempotent, never overwriting. A sponsor `logoUrl` is never derived from the name (null until an upload); a client value is only accepted when it is the current one or a file in the own directory (`resolveClientLogoUrl`; a backup restore accepts any valid file name). Logo uploads accept only png/jpg/gif/webp, checked on the content, at most 4096×4096 pixels and (PNG) with sound data (`services/imageUpload.ts`, `services/imageSafety.ts`); there is no generic upload endpoint. Files are read for the PDF and the image download only through `readAssetFile`/`assetFilePath` (`services/reportSponsors.ts`): regular files inside the root, no symlinks, size-limited, read once; `doc.image` gets the checked buffer from `pdfImage`.
- **Backup coverage**: the per-entity backups (`routes/backup.ts`) carry every tenant field of persons/skills, positions, matches (also `isManual`), productions (`liveTime`, `setupTime`, `crewCallTime`, callsheet `timeStart/timeEnd`, events `planned*`, `callSheetItemId`, `parentId`, `metadata`, report `matchSponsor/ballSponsor`), sponsors (also `enabled`, `categories`, logo file name) and all `OrganizationSetting` keys. Productions carry `chapters` (name, orderIndex, bezetting) and `chapterOrderIndex` on items and events; files with the old `segments`/`productionSegmentVolgorde` and old segment-template backups are still read. Settings also carry the own club (`ownClubSlug`), the organization details (`organizationDetails`: name, logo, club; a restore never changes the target's slug or `isActive`) and the seasons' `indoorStartDate` by season name (set only when the season exists without one). Clubs carry each player's `seasonName`; players without one (backups from before the seasons) are never put in the active season silently: the restore answers 400 `PLAYER_SEASON_REQUIRED` (with `playersWithoutSeason`, nothing written) unless `?seasonId=` names their season, and the Backup page then asks for it. Images: `GET /api/backup/images` (zip relative to `ASSETS_DIR`). Not carried, intentionally: `MatchSource` and API keys (secrets); also not carried: callsheet/title templates, `PositionLink`, `MatchRoleAssignment` (the standard set covers most). `StatsMatch` (kept statistics matches) is not in the per-entity backups either: the bridge fills it again from the statistics databases, and `pg_dump` / the backup of `upgrade.cmd` carry it.
- **Base images are Docker Hardened Images** (`dhi.io/node`, `dhi.io/nginx`); run `docker login dhi.io` (Docker Hub account) once before building. `-dev` variants only in build stages; runtime images have no shell, no npm/pnpm and run as non-root (API as uid 1000, nginx on port 8080 → host 80). Hence: the migrate job runs `node /app/seed/migrate-and-seed.cjs`, healthchecks use `node -e fetch(...)`, the Prisma schema engine (only `prisma migrate deploy` needs it; Prisma 7 has no query engine) is pinned via `PRISMA_SCHEMA_ENGINE_BINARY`. PostgreSQL still uses the official `postgres:16-alpine` image.
- **Local image test against a backup**: `docker-compose-localtest.yml` (project `korfbal-localtest`, ports 80/3334/5433) builds the images and fills its own db from a pg_dump SQL file on first start (`LOCALTEST_SQL`, relative to `distribution/`, default `../../2025-2026-backup/streamz-2025.sql`); the migrate job runs with `SKIP_SEED=true`. Images come from a bind mount on the local disk (`LOCALTEST_STORAGE`, default `../storage`, the repo's `storage/`), so they survive restarts. Reset the db to the backup: `down -v` then `up -d`. `distribution/start-localtest.sh` (Windows: `start-localtest.cmd`, `[--only streamz|bridge] [--no-build] [--reset] [--stop]`) builds and starts localtest plus the venue-bridge from source (same project and network, `API_URL` defaults to `http://korfbal-streamz-api:3333`) with the settings from `localtest.local.env` (gitignored, template `localtest.local.env.example`); without `API_KEY` it starts only Streamz and says where to create the key. The API serves `/uploads` and `/storage` from `ASSETS_DIR`; there is no separate uploads dir.
- **Docker Hub overview**: `apps/<app>/DOCKERHUB.md` is published as the repository description on Docker Hub by the `merge` job in `ci.yml`, on releases only. Keep it up to date when env vars, ports or the purpose change.
- **Venue-bridge (one per venue)**: `apps/venue-bridge` is its own app and image (`mvanvendeloo/streamz-kit-venue-bridge`, `STREAMZ_BRIDGE_VERSION`); it is not in the main compose files and connects out to the API's socket path `/venue-bridge-socket` (a reverse proxy in front of the API must forward it with WebSocket upgrade, like `/socket.io/`; the kit's nginx.conf and Vite proxy do) (`API_URL`, `API_KEY` of an organization key, `BRIDGE_NAME`), so the API can run in the cloud. The compose files are in `distribution/`: `docker-compose.venue-bridge-dev.yml` (dev/localtest, builds from source, service `venue-bridge` on `korfbal-network`, data in the repo's `data/venue-bridge`) or `docker-compose.venue-bridge.yml` (Docker Hub image, project `venue-bridge`, data in `distribution/data/venue-bridge`), plus one `distribution/variants/*.yml` for the statistics source: `mac` (bind `/Volumes/KL2627:/stats:ro`), `windows-robocopy` (bind `C:/streamz/stats:/stats:ro`, filled by `distribution/scripts/sync-stats.ps1`), `cifs` (volume; the bridge does not start when the PC is off; Docker keeps a created volume's options, so `docker volume rm` after changing them), `page-only`; without a variant (dev) `distribution/local-html`. `distribution/scripts/venue-bridge-start.sh|.ps1 [variant]` runs it (`PROD=1`/`-Prod` for the production file; `mount-share-mac.sh` mounts the share on a Mac); in production on Windows `start.cmd` does. Local env of the bridge: `API_URL`, `API_KEY`, `BRIDGE_NAME`, `STATS_DIR`, `COPY_DIR` (`/data`, owned by uid 1000), `CONFIG_FILE`, `PORT`, `HOST`, `LOG_LEVEL`; the device addresses and statistics settings are set in Instellingen and sent by the API (the compose rewrite for the venue comes with the delivery tasks). `npm run bridge:dev|bridge:build|bridge:test`; CI builds, tests and publishes it like the other apps (affected only). The API image does not know `STATS_DIR`, `SCOREBOARD_BASE_URL` or `SHOTCLOCK_BASE_URL` any more.
- **No secrets in checked-in config**: compose files read them via `env_file` from local, gitignored files next to them in `distribution/` — `secrets.env` (dev and localtest, optional), `secrets.prod.env` (prod) — and `streamz-test/secrets.env`. Templates: `distribution/secrets.env.example`, `distribution/secrets.prod.env.example`. Don't use a root `.env`/`.env.local` for this: Nx loads those into every task.

## Environment Variables (API)

Validated with Zod at startup (`apps/korfbal-stream-api/src/config.ts`):

```
DATABASE_URL=postgresql://korfbal:korfbal@localhost:5432/korfbal
PORT=3333
ASSETS_DIR=storage
HOST_IP=<optional, for vMix endpoint auto-detection in Docker>
DEBUG_LOGGING=<optional, true: also log every successful GET (vMix, scoreboard polling) and the vMix data source content; LOG_LEVEL overrides>
```

The match import is not an env var: each organization configures its source (provider, URL, token) in Beheer → Setup → Organisatie → Wedstrijdimport (`MatchSource`).

In tests, `.env.test` is loaded automatically.
