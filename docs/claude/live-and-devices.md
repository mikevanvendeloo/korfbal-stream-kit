# LIVE, live state and devices

- **Two apps, one frontend build**: LIVE (`app/LiveApp.tsx`) is served from the root (`/`, `/scoreboard`, `/callsheet[/<positie>]`, `/show-caller[/<positie>]`: always the active production, no production id in the address; `ActiveProductionRoute` provides it (`useLiveProductionId()`) and follows the socket event `active_production_changed` that activation and an active import emit; old addresses with an id are rewritten once) and is read-only except the interview selection and operating vMix (`/vmix`); its nav has a "Beheer" link to `/admin`. Beheer (`app/AdminApp.tsx`, lazy-loaded) lives under `/admin/*`, with URLs following its menu (`producties`, `stamgegevens` (also the draaiboek templates), `rapportages`, `setup` (organisatie: under the organization logo next to "Wissel organisatie"; organisaties: gear menu), `tools` (gear menu, next to Instellingen, Organisaties, licht/donker and Over deze app)). All Beheer URLs come from `lib/adminPaths.ts` — never write them by hand. A production's pages share the tabs in `components/ProductionLayout.tsx`. Both apps share the same pages/components; no redirects from old URLs.
- **Single active production**: one active production per organization: `POST /api/production/:id/activate` and the production import deactivate the others of that organization only (the extension scopes the update).
- **LIVE hall lane**: Volgend/Vorig step through Stream items and samenkomstpunten only; Zaal items in a block that also has Stream items run by themselves (`activeVenueEventId`/`activeVenueStartTime` in `liveStateSnapshot()`, socket `venue_event_update`, own timer per organization, cleared by `discardLiveState`). The first Stream item of a block starts its hall lane, each next Zaal item starts when the previous one's duration is over, `POST /api/production/:id/venue-next` (Zaal ›) moves on by hand, and a samenkomstpunt or another block ends the running hall item (actual end in `ProductionEvent.metadata.actualEndTime`). A block with only Zaal items is stepped through with Volgend as before.
- **In-memory state, per organization**: live production state (`productionId`, `activeEventId`, clocks, `isClockRunning`, the clock interval and auto-advance timer) lives in `productionState.ts` in memory, one per organization (`Map<organizationId, state>`); `timeSyncService` (the production clock) likewise. Every exported function works on the organization in the context, so call them from a request or inside `runWithOrganization`; timers are bound with `bindOrganization`. Send `liveStateSnapshot()` to clients, never `getCurrentState()` (it holds the timers). On startup the active production of every organization is restored; on restart the state resets otherwise.
- **Socket.io rooms**: the handshake sends `auth: {organization: <slug>}`; `services/socket.ts` resolves it to an active organization and joins room `org:<id>` (unknown/inactive/malformed slug → `connect_error` "Onbekende of inactieve organisatie" with `data.code` `ORGANIZATION_UNKNOWN`; no slug → connected, but only the global events). Every live emit goes through `emitToOrganization(event, …)` (room of the organization in the context), never `io.emit`; only `heartbeat` and `season_changed` are global. Every state change calls `broadcastState()`; clients receive snapshots, not diffs. Handshakes from a page on another host are refused (`isSameOriginRequest`, see **Same-origin rule**).
- **Background services per organization**: `vmixCallsheetPushService` runs every second for each organization whose show runs, read from the live state in memory (`liveOrganizationIds()`: no database query per second while no show runs; switched-off organizations have no live state), each with its own settings; it sends its vMix commands through that organization's venue-bridge (`vmix:call`, one batch per tick; an organization without a bridge is skipped, logged once per disconnect). What was pushed last is remembered per organization. One organization's slow bridge must never hold up another: a busy flag per organization, a try/catch per organization, and a deadline on every question to a bridge (`askBridge`). The API makes no outgoing request to devices itself (scoreboard, shot clock, statistics PC, vMix): the venue-bridge does, with wall-clock deadlines (`signal: AbortSignal.timeout(ms)` plus `maxContentLength`, never axios' `timeout`, which is an idle timeout).
- **Venue clock (zaalklok)**: the scoreboard is the only source, read by the venue-bridge and pushed as a `clock` reading (`services/venueData.ts` feeds a current reading of a running show to `updateVenueClock`; also `POST /api/show/clock` and `POST /api/time/venue-clock`). `updateVenueClock` (`productionState.ts`) stores `clocks.scoreboardTime` and emits `venue_clock_update {scoreboardTime}` only when the time changed. Clients show that value as it is and never count on locally (it stands still at every stoppage of zuivere speeltijd, and device clocks differ from the server). `time_state_update` is the production clock only: never send the venue clock through it.
- **Switching an organization off**: `PUT /api/organizations/:id` with `isActive: false` calls `stopOrganization()` (`services/organizationLifecycle.ts`): clock and auto-advance timer stop, its entries in `liveStates`, `timeStates` and `pushMemories` are dropped and its sockets are closed (`disconnectOrganizationSockets`); the database is left alone. Switching it on again restores its active production (`resumeOrganization`). Add any new per-organization in-memory map to `stopOrganization`.
- **Several vMix instances**: the `vmixInstances` setting holds the vMix PCs (e.g. stream PC and screen PC) and per function which one it sends to (`services/vmixInstances.ts`, `resolveVmixInstance(fn)` in the API for settings and answers; the venue-bridge resolves the instance itself from its configuration, empty target = first instance). Add new functions to `VMIX_FUNCTIONS` (`libs/venue-protocol`, kit hook). The old single `vmixWebUrl` setting mirrors the first instance. Schemas live once in `libs/venue-protocol`.
- **Callsheet → vMix**: `services/callsheetTiming.ts` derives the current/next item per position (same rule as the Show Caller: items without positions count for everyone). `services/vmixCallsheetPush.ts` computes what changed every second (when enabled in the `vmixCallsheetPush` setting; SetText/SetColor/SetTextColour, full resend every 15s) and sends the commands as one `vmix:call` batch through the venue-bridge (`services/vmixBridge.ts`); the function URL builder lives in the bridge. vMix answers 200 to an unknown input or field, so `checkCallsheetTarget` checks them against the inputs the bridge reads (`vmix:inputs`, `GET /api/vmix/inputs`) on a manual push. Without a connected bridge the routes answer 503 `VENUE_BRIDGE_OFFLINE`.
- **Interview placeholders**: callsheet titles/notes may contain `{speler|coach-thuis|uit|eigen|tegenstander[:kort|:achternaam]}`. They're stored as typed and only filled in when shown (LIVE callsheet/Show Caller via `InterviewNamesProvider`, vMix timing). The parser exists twice — `apps/korfbal-stream-api/src/services/interviewPlaceholders.ts` and `apps/korfbal-stream-kit/src/lib/interviewPlaceholders.ts` — keep them in sync. Each placeholder segment says whom it names (`side`, `role`); `/interview-names` also returns `people` (name, shirtNo, photoUrl), so `InterviewText photos` shows a small `InterviewAvatar` (photo, else shirt number, else initials; coaches always initials) next to the name: in the callsheet everywhere, in the Show Caller only at the current and next item, unless the device setting "Interviewfoto's" (`hooks/useInterviewPhotos.ts`) is off. LIVE → Interviews (`/interviews`) uses `/interview-cards`; a saved choice emits socket `interviews_updated` `{productionId}` and the kit refetches (`useInterviewsUpdatedRefresh`), with the 10 s poll as fallback.
- **LIVE on phones**: LIVE is used on phones (e.g. 360 px wide). Nothing may be wider than the screen: one wide element makes the whole page wider, and then the sticky headers (Show Caller controls, clocks) scroll out of view. Use `truncate`/`min-w-0`/`flex-wrap` and check at 360 px. Below 768 px the Show Caller renders `components/ShowCallerPhone.tsx` (now/next/later, controls fixed at the bottom); its actions go through `hooks/useShowControls.ts`, which shows failures on screen. LIVE finds the active production with `GET /api/production/active` (`useActiveProduction`), independent of the active season.

- **Venue-bridge (`apps/venue-bridge`, `libs/venue-protocol`)**: its own Docker image (`mvanvendeloo/streamz-kit-venue-bridge`, port 3340), one per venue, the only part that talks to the venue network: scoreboard, shot clock, statistics PC and vMix. It connects out to the API's second socket.io server (`services/venueBridgeSocket.ts`, path `/venue-bridge-socket`, default namespace; `VENUE_BRIDGE_PATH` in the lib) with an organization API key (`auth.key`, `X-Api-Key` header or `?key=`; `connect_error` with `data.code` `API_KEY_MISSING`/`API_KEY_INVALID`, also for a revoked key or an inactive organization; the key is never logged; the server-wide same-origin rule applies). One socket per organization: a new one replaces and disconnects the old (`services/venueBridge.ts`); `askBridge(event, payload, {deadlineMs, maxBytes, schema})` asks the bridge of the organization in the context and throws `BridgeOfflineError` (503 `VENUE_BRIDGE_OFFLINE`, in both apiErrorCodes files) for no bridge, a timeout, a too large or malformed answer. The bridges' server has `maxHttpBufferSize` 11 MB (statistics answers) and the same same-origin `allowRequest`; the browsers' server keeps the default 1 MB. Both servers run on the one http server with `destroyUpgrade: false`, so neither kills the other's websocket upgrades. A reverse proxy must forward `/venue-bridge-socket/` with WebSocket upgrade like `/socket.io/` (kit `nginx.conf` and the Vite dev proxy do). Events and zod schemas: `libs/venue-protocol` (`venue:reading`, `config:apply`, `stats:request`, `vmix:call`, `vmix:inputs`); the lib resolves through the tsconfig path alias, and API and bridge builds use `bundle: true` + `thirdParty: false` so it is bundled while npm packages stay external.
- **Venue data**: `services/venueData.ts` keeps per organization the latest `score`, `clock` and `shotclock` reading (validated: device enum, array of at most 20 items, 4 KB). A reading is current when ok, less than 10 s old and its bridge connected; `/api/scoreboard`, `/clock`, `/shotclock` (shot clock with `color`: red <= 10, orange <= 15) answer from it or 502 `Failed to fetch …`. `GET /api/venue-bridge/status` (organization or feed key) answers `{connected, name, version, pageUrl, connectedAt, config: {state, error}, devices}`; socket `venue_bridge_status` (same body) goes to the organization's clients when the connection, configuration state or a device state changes, not on ages.
- **Venue configuration**: central. `services/venueConfig.ts` builds `{scoreboard, shotclock, stats, vmix, version}` from the settings `scoreboardUrl`/`shotclockUrl`, `matchStats` and `vmixInstances` and sends it with `config:apply` on connect and 500 ms (debounced) after saving any of them (`scheduleVenueConfigPush()` in the settings routes). The bridge validates, applies and caches it; a refusal shows in the status. Never put keys or another organization's data in it.
- **Match statistics**: `/api/stats/*` keep their URLs, feed keys and `X-Stats-*` headers; the API asks the bridge over `stats:request` (`services/stats/statsBridge.ts`: 5 s deadline, 10 MB, 2 s cache per organization and path, one in-flight request per path, 2 s offline memory) and passes the answer on; the bridge's own refusals (an `error` with an error status) pass through. Organization setting `matchStats` is `{pageUrl, mdbPath, mdbEnabled, shareHost, keepCopy}` (zod `MatchStatsSchema`: relative paths without `..`, `.mdb`/`.accdb`, `.html` or http(s)); old `bridgeUrl` and the old token key `matchStatsBridgeToken` are ignored and left out of the settings backup. `GET /api/stats/status` is always 200: `{bridge: {ok, ms}, ...the bridge's connection test}` (cached 3 s, shared in-flight); the kit gates the Statistieken page on `bridge.ok`. `/api/stats` and `/api/venue-bridge/status` are in `FEED_API_PATHS`.
- **Statistics `{team}`**: the API asks the bridge with `?team=<n>` (`services/stats/statsTeam.ts` stays in the API: the trailing ` <digits>` of the own team of the active production, default 1; cached 3 s) and rewrites the bridge's team to `{value, from: 'production' | 'default'}` (body `team`, header `X-Stats-Team: 2; from=production`). `/live/players` keeps its own `team=home|away`.
- **The bridge's insides** (`apps/venue-bridge`, README there): start settings only from env (`API_URL`, `API_KEY`, `BRIDGE_NAME`, `STATS_DIR`, `COPY_DIR`, `PORT`, `HOST` (0.0.0.0), `CONFIG_FILE` (`/data/venue-bridge.json`), `LOG_LEVEL`; no `API_URL`/`API_KEY` = exit code 1, the key is never logged); everything about the venue (device URLs, `pageUrl`, `mdbPath`, `mdbEnabled`, `shareHost`, `keepCopy`, vMix instances) comes from the API's configuration and is cached (atomic write, mode 600). It reads the devices every second (800 ms deadline, 4 KB, one request in flight per device, sends changes plus every 5 s), carries out `vmix:call`/`vmix:inputs`, and serves a fallback API on the venue network with the API key (`/api/scoreboard*`, `/api/stats/*`, `POST /api/vmix/set-timer`, `/bridge/status`, `/health`). The statistics routes below are in-process handlers (`services/statsHandler.ts`) for `stats:request` and the fallback. Routes `/health`, `/status`, `/live`, `/live/players`, `/matches` (without a usable database one synthetic `live` entry with `source: 'page'`), `/matches/:table/actions|players` (`live`: the page's players), `/players`, `/current/players` (database, else the page rows with `source: 'page'`; `X-Stats-Database: disabled|unreachable`). Page parser: linear, 512 KB, row/cell caps, no redirects. Share access: path resolution (relative, no `..`, .mdb/.accdb or .html, real path inside the root, size limit), one operation at a time with a 3 s deadline, doubling down window (5 s to 60 s), SMB port probe first (cached 5 s), stamp-based re-read (at most every 10 s), local copy `<COPY_DIR>/<hash of the path>-<file>` at most every 5 minutes, used when STATS_DIR is unset, the PC does not answer or the file is missing (never for a refused path or without KEEP_COPY). mdb-reader runs in a worker thread (inline script, 10 s limit, then terminate and 502). The match is the one with the latest action. Team statistics and top scorers (`services/teamStats.ts`, pure functions): `/team-stats` (two flat rows: goal, rebound, strafworp, vrije bal, afstand, kort, doorloop percentages, goals by women/men from `spelersover` SEX, and attack figures from the page's attempts-per-possession distribution: attacks = goals + turnovers, average attempts per attack = sum(n x count) / attacks) and `/top-scorers` (per team most goals first, ties by fewer attempts), both of the match with the latest action, from the page when the database is off (no sex then); the API asks for them like the other routes; the kit shows them as the tabs Teamstatistieken and Topscorers. Match analysis (`services/matchAnalysis.ts`, pure, `/analysis`, LIVE page Analyse `/analyse`): database only (503 "De analyse heeft het statistiekenbestand nodig" without it, 400 for a refused path), memoized per file read. A possession is a run of actions with one `opstelling` (it changes at every change of possession, also after a goal without `NAAR ANDER VAK`); vak 1 = lineup pairs starting in AANVAL (definition rows `optelveld` 0 before `START WEDSTRIJD`), a substitute takes the vak of the player replaced; score from goal codes (the score columns stay 0); halves from RUST/START TWEEDE HELFT; turnovers: own on a minus in AANVAL, opponent on a plus in VERDEDIGING, neutral 4xxx for the attacker. `tijdtotaal` is the statistics PC clock (longer than the 25 min pure playing time per half). Compose overrides and scripts: `apps/venue-bridge/compose/`, `scripts/venue-bridge/`.
