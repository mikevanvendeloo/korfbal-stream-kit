# LIVE, live state and devices

- **Two apps, one frontend build**: LIVE (`app/LiveApp.tsx`) is served from the root (`/`, `/scoreboard`, `/callsheet/...`, `/show-caller/...`) and is read-only except the interview selection and operating vMix (`/vmix`); its nav has a "Beheer" link to `/admin`. Beheer (`app/AdminApp.tsx`, lazy-loaded) lives under `/admin/*`, with URLs following its menu (`producties`, `stamgegevens` (also the draaiboek templates), `rapportages`, `setup` (organisatie: under the organization logo next to "Wissel organisatie"; organisaties: gear menu), `tools` (gear menu, next to Instellingen, Organisaties, licht/donker and Over deze app)). All Beheer URLs come from `lib/adminPaths.ts` — never write them by hand. A production's pages share the tabs in `components/ProductionLayout.tsx`. Both apps share the same pages/components; no redirects from old URLs.
- **Single active production**: one active production per organization: `POST /api/production/:id/activate` and the production import deactivate the others of that organization only (the extension scopes the update).
- **LIVE hall lane**: Volgend/Vorig step through Stream items and samenkomstpunten only; Zaal items in a block that also has Stream items run by themselves (`activeVenueEventId`/`activeVenueStartTime` in `liveStateSnapshot()`, socket `venue_event_update`, own timer per organization, cleared by `discardLiveState`). The first Stream item of a block starts its hall lane, each next Zaal item starts when the previous one's duration is over, `POST /api/production/:id/venue-next` (Zaal ›) moves on by hand, and a samenkomstpunt or another block ends the running hall item (actual end in `ProductionEvent.metadata.actualEndTime`). A block with only Zaal items is stepped through with Volgend as before.
- **In-memory state, per organization**: live production state (`productionId`, `activeEventId`, clocks, `isClockRunning`, the clock interval and auto-advance timer) lives in `productionState.ts` in memory, one per organization (`Map<organizationId, state>`); `timeSyncService` (the production clock) likewise. Every exported function works on the organization in the context, so call them from a request or inside `runWithOrganization`; timers are bound with `bindOrganization`. Send `liveStateSnapshot()` to clients, never `getCurrentState()` (it holds the timers). On startup the active production of every organization is restored; on restart the state resets otherwise.
- **Socket.io rooms**: the handshake sends `auth: {organization: <slug>}`; `services/socket.ts` resolves it to an active organization and joins room `org:<id>` (unknown/inactive/malformed slug → `connect_error` "Onbekende of inactieve organisatie" with `data.code` `ORGANIZATION_UNKNOWN`; no slug → connected, but only the global events). Every live emit goes through `emitToOrganization(event, …)` (room of the organization in the context), never `io.emit`; only `heartbeat` and `season_changed` are global. Every state change calls `broadcastState()`; clients receive snapshots, not diffs. Handshakes from a page on another host are refused (`isSameOriginRequest`, see **Same-origin rule**).
- **Background services per organization**: `vmixCallsheetPushService` and `venueClockSyncService` run every second for each organization whose show runs, read from the live state in memory (`liveOrganizationIds()`: no database query per second while no show runs; switched-off organizations have no live state), each with its own settings, vMix and scoreboard (what was pushed last is remembered per organization). One organization's slow device must never hold up another: a busy flag per scoreboard URL / per organization, a try/catch per organization, and a wall-clock deadline on every outgoing device request (`signal: AbortSignal.timeout(ms)`, plus `maxContentLength` for small answers). Never use axios' `timeout` option: it is an idle timeout, so a server that drips bytes keeps the request open.
- **Venue clock (zaalklok)**: the scoreboard is the only source. `updateVenueClock` (`productionState.ts`, from `venueClockSyncService` every second, `POST /api/show/clock` and `POST /api/time/venue-clock`) stores `clocks.scoreboardTime` and emits `venue_clock_update {scoreboardTime}` only when the time changed. Clients show that value as it is and never count on locally (it stands still at every stoppage of zuivere speeltijd, and device clocks differ from the server). `time_state_update` is the production clock only: never send the venue clock through it.
- **Switching an organization off**: `PUT /api/organizations/:id` with `isActive: false` calls `stopOrganization()` (`services/organizationLifecycle.ts`): clock and auto-advance timer stop, its entries in `liveStates`, `timeStates` and `pushMemories` are dropped and its sockets are closed (`disconnectOrganizationSockets`); the database is left alone. Switching it on again restores its active production (`resumeOrganization`). Add any new per-organization in-memory map to `stopOrganization`.
- **Several vMix instances**: the `vmixInstances` setting holds the vMix PCs (e.g. stream PC and screen PC) and per function which one it sends to (`services/vmixInstances.ts`, `resolveVmixInstance(fn)`; empty target = first instance). Anything that sends commands to vMix must resolve its instance this way — add new functions to `VMIX_FUNCTIONS` (API schema and kit hook). The old single `vmixWebUrl` setting mirrors the first instance.
- **Callsheet → vMix**: `services/callsheetTiming.ts` derives the current/next item per position (same rule as the Show Caller: items without positions count for everyone). `services/vmixCallsheetPush.ts` pushes it every second (when enabled in the `vmixCallsheetPush` setting) with SetText/SetColor/SetTextColour, sending only changed fields plus a full resend every 15s. Build every vMix function call with `buildVmixFunctionUrl` (`services/appSettings.ts`: `/api/?`, values with `encodeURIComponent`, so a space is `%20`). vMix answers 200 to an unknown input or field, so `checkCallsheetTarget` checks them against its XML state (`services/vmixInputs.ts`, `GET /api/vmix/inputs`) on a manual push.
- **Interview placeholders**: callsheet titles/notes may contain `{speler|coach-thuis|uit|eigen|tegenstander[:kort|:achternaam]}`. They're stored as typed and only filled in when shown (LIVE callsheet/Show Caller via `InterviewNamesProvider`, vMix timing). The parser exists twice — `apps/korfbal-stream-api/src/services/interviewPlaceholders.ts` and `apps/korfbal-stream-kit/src/lib/interviewPlaceholders.ts` — keep them in sync. Each placeholder segment says whom it names (`side`, `role`); `/interview-names` also returns `people` (name, shirtNo, photoUrl), so `InterviewText photos` shows a small `InterviewAvatar` (photo, else shirt number, else initials; coaches always initials) next to the name: in the callsheet everywhere, in the Show Caller only at the current and next item, unless the device setting "Interviewfoto's" (`hooks/useInterviewPhotos.ts`) is off. LIVE → Interviews (`/interviews`) uses `/interview-cards`; a saved choice emits socket `interviews_updated` `{productionId}` and the kit refetches (`useInterviewsUpdatedRefresh`), with the 10 s poll as fallback.
- **LIVE on phones**: LIVE is used on phones (e.g. 360 px wide). Nothing may be wider than the screen: one wide element makes the whole page wider, and then the sticky headers (Show Caller controls, clocks) scroll out of view. Use `truncate`/`min-w-0`/`flex-wrap` and check at 360 px. Below 768 px the Show Caller renders `components/ShowCallerPhone.tsx` (now/next/later, controls fixed at the bottom); its actions go through `hooks/useShowControls.ts`, which shows failures on screen. LIVE finds the active production with `GET /api/production/active` (`useActiveProduction`), independent of the active season.

- **Match statistics = a separate, temporary app (`apps/statistics-bridge`)**: its own Docker image (`mvanvendeloo/statistics-bridge`, port 3340, one bridge per venue/statistics PC, no organizations, no database), so a failing share or PC only takes down the bridge. Kit and vMix keep using `/api/stats/*` with the same URLs and API keys; the API is a thin client (`routes/stats.ts`, `services/stats/statsBridge.ts`) that forwards GET to `<bridgeUrl>/<same path>`. Organization setting `matchStats` is `{bridgeUrl}` only (older pageUrl/mdbPath/keepCopy/shareHost values are ignored); the bridge token is a write-only secret under its own key `matchStatsBridgeToken` (`getBridgeToken`, never returned: `GET /api/settings/match-stats` answers `hasBridgeToken`; removed when the bridge's origin changes without a new token; excluded from the settings backup export and import). The forward uses `AbortSignal.timeout(5000)`, `maxContentLength`, `maxRedirects: 0`, a 2 s per-organization cache with one in-flight request per path, and passes the `X-Stats-*` headers. Unreachable, timeout, a redirect or an answer that is not the bridge's JSON gives 503 `{error: 'De statistics bridge is offline', code: 'STATS_BRIDGE_OFFLINE'}` (code in both apiErrorCodes files); the bridge's own refusals (409/503 with an `error`) pass through, a refused token becomes 502 without echoing it. `GET /api/stats/status` is always 200: `{bridge: {ok, ms}, ...the bridge's connection test}` (cached 3 s, shared in-flight); the kit gates the Statistieken page on `bridge.ok` ("De statistics bridge is offline"). `/api/stats` stays in `FEED_API_PATHS`.
- **Statistics `{team}`**: the API asks the bridge with `?team=<n>` (`services/stats/statsTeam.ts` stays in the API: the trailing ` <digits>` of the own team of the active production, default 1; cached 3 s) and rewrites the bridge's team to `{value, from: 'production' | 'default'}` (body `team`, header `X-Stats-Team: 2; from=production`). `/live/players` keeps its own `team=home|away`.
- **The bridge** (`apps/statistics-bridge`, README there): env `PORT`, `STATS_DIR`, `PAGE_URL` (http(s) or relative .html in STATS_DIR), `MDB_PATH` (`{team}` allowed), `MDB_ENABLED` (false: nothing of the database, share or copy is touched; only the page), `SHARE_HOST`, `KEEP_COPY`, `COPY_DIR` (`/data`), `BRIDGE_TOKEN` (every route but `/health` needs `X-Bridge-Token`, timing-safe). Routes `/health`, `/status`, `/live`, `/live/players`, `/matches` (without a usable database one synthetic `live` entry with `source: 'page'`), `/matches/:table/actions|players` (`live`: the page's players), `/players`, `/current/players` (database, else the page rows with `source: 'page'`; `X-Stats-Database: disabled|unreachable`). Page parser: linear, 512 KB, row/cell caps, no redirects. Share access: path resolution (relative, no `..`, .mdb/.accdb or .html, real path inside the root, size limit), one operation at a time with a 3 s deadline, doubling down window (5 s to 60 s), SMB port probe first (cached 5 s), stamp-based re-read (at most every 10 s), local copy `<COPY_DIR>/<hash of the path>-<file>` at most every 5 minutes, used when STATS_DIR is unset, the PC does not answer or the file is missing (never for a refused path or without KEEP_COPY). mdb-reader runs in a worker thread (inline script, 10 s limit, then terminate and 502). The match is the one with the latest action. Team statistics and top scorers (`services/teamStats.ts`, pure functions): `/team-stats` (two flat rows: goal, rebound, strafworp, vrije bal, afstand, kort, doorloop percentages, goals by women/men from `spelersover` SEX, and attack figures from the page's attempts-per-possession distribution: attacks = goals + turnovers, average attempts per attack = sum(n x count) / attacks) and `/top-scorers` (per team most goals first, ties by fewer attempts), both of the match with the latest action, from the page when the database is off (no sex then); the API forwards them like the other routes; the kit shows them as the tabs Teamstatistieken and Topscorers. Match analysis (`services/matchAnalysis.ts`, pure, `/analysis`, LIVE page Analyse `/analyse`): database only (503 "De analyse heeft het statistiekenbestand nodig" without it, 400 for a refused path), memoized per file read. A possession is a run of actions with one `opstelling` (it changes at every change of possession, also after a goal without `NAAR ANDER VAK`); vak 1 = lineup pairs starting in AANVAL (definition rows `optelveld` 0 before `START WEDSTRIJD`), a substitute takes the vak of the player replaced; score from goal codes (the score columns stay 0); halves from RUST/START TWEEDE HELFT; turnovers: own on a minus in AANVAL, opponent on a plus in VERDEDIGING, neutral 4xxx for the attacker. `tijdtotaal` is the statistics PC clock (longer than the 25 min pure playing time per half). Compose overrides and scripts: `apps/statistics-bridge/compose/`, `scripts/statistics-bridge/`.
